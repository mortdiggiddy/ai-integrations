# Confidential runtime protocol candidate

Status: LATER STAGE GUIDANCE, 2026-10-26. Concrete engineering candidate for M2 through M4, with bounded independent review of its safety and admission contracts. Not implemented or runtime qualified. It is not a prerequisite for the M1 orchestrator contribution. This document supplies application contracts, not new Claude SDK APIs. It grants no execution permission and does not establish a whole-project PASS. The [decision register](decisions.md) owns approval status; the [specification](spec.md) owns requirements.

## Ownership and durable identities

The outside Session Workflow is sole accepted-head owner. The existing harness controller is sole compute owner. The protected Entity authority is sole owner of nonrepeatable dispatch admission. The inside supervisor owns native SDK/CLI execution, input consumption, capture and content policy. Generated code has no supervisor signing key, store/key administration credential, control socket or Temporal credential. The controller, authority and retained store remain outside disposable execution.

The trusted gateway conditionally reserves a random lineage before first start, binding job, Workflow identity and immutable start-input digest. Reset and Continue-As-New retain this lineage. Each compute incarnation has an immutable provider ID and a monotonically admitted generation. Timeout, disconnected observation or expired lease cannot authorize another generation. Replacement first requires independent terminal evidence for the exact old incarnation and confined descendants, then a generation transition through the retained owners. Already issued external effects remain separately classified.

Every operation carries `protocol_version`, authenticated `principal`, `job_id`, `lineage`, `generation`, `operation_id`, `request_digest`, `policy_digest` and an expiry. Content fields are authenticated ciphertext with scope/schema associated data. The receiver derives authorization from authenticated identity and admitted policy, never from a caller-supplied role. Canonical request bytes bind the digest. Reuse of an operation ID with a different digest is a conflict, not a retry.

The receiver retains operation records before mutation and answers duplicate requests with the retained state/result. The states are `REGISTERED`, `IN_PROGRESS`, `SUCCEEDED`, `REFUSED` and `UNCERTAIN`. A crash after intent publication but before a definitive result returns `UNCERTAIN` until reconciliation can supply evidence. It never becomes affirmative nonexecution because a response is missing. The original request and identity are retained across retries, reset and handoff.

## Restricted operation contract

These are proposed application wire operations. Their implementation can use Activities, an authenticated service and provider adapters; they are not claimed upstream methods.

| Operation | Additional input | Durable response and consequence |
|---|---|---|
| `CreateOrReconcile` | Admitted provider/image/configuration digests and launch identity | Exact resource ID and original launch binding, or `UNCERTAIN`. Provider identity reconciliation precedes any create retry. No retry creates under a fresh identity. |
| `Attach` | Exact resource ID, generation and approved readiness evidence | Short lived scoped channel binding. Reattachment neither launches a CLI nor grants a new input consumer. |
| `SubmitInput` | Sealed input, client signature, sequence and predecessor input digest | Receipt only after immutable input persistence and a deduplicated sequence reservation. Receipt means accepted input, not completed turn or accepted recovery state. One native consumer per incarnation claims the retained input identity. |
| `Observe` | Existing generation and permitted event cursor | Bounded status events through the release gate. A cursor is diagnostic progress, not checkpoint authority. Observer cancellation closes observation only. |
| `CaptureStoppedEpoch` | Expected predecessor head, epoch identity and capture reason | Exact candidate manifest reference after stopped-state capture. It is not accepted until the Session head transaction below succeeds. |
| `ReadAccepted` | Exact accepted head/version and admitted reader identity | Matching authenticated encrypted objects or classified refusal. Never select an independent latest object. |
| `RequestStop` | Exact resource identity and reason | Retained stop intent and requested action. It does not assert death. The controller, not a borrowed observer, owns compute removal. |
| `InspectTerminal` | Exact launch/resource identity | Independently authenticated terminal evidence and confinement scope, or `UNCERTAIN`. A job supplied receipt cannot satisfy it. |
| `Reconcile` | Original operation identity and digest | Retained operation status and exact result/evidence. No implicit second execution. |

No operation exposes arbitrary guest exec, plaintext native protocol messages or arbitrary Workflow administration. Submission authentication does not give the client a combined recovery key. Sealed content remains inside the selected content boundary; outside histories, failures and logs carry permitted references/status only.

## Finite synthetic operation profile

Carry forward the [approved local configuration](../../python/claude_agent_sdk/docs/skill-recovery/proposals/distributed-recovery/2026-10-08/dsr-0.6-configuration.md#approved-local-configuration-2026-10-14): one session, one retained pending call, one harmless effect, 600 second case deadline, 120 CPU seconds and its existing byte/process bounds. The following are proposed engineering timeout values for that profile, not production SLOs or claims about installed infrastructure.

| Operation | Attempt bound | Total bound and retry rule |
|---|---|---|
| Create/reconcile resource and readiness | 120 seconds | 180 seconds, at most two mutating attempts and only after original identity reconciliation |
| Attach, submit, exact reads and other short RPCs | 30 seconds | 60 seconds, at most two identical requests with receiver deduplication |
| Observe | 30 seconds | Each observation invocation ends after 30 seconds; heartbeat every 5 seconds with 15 second heartbeat timeout; reconnect uses the same generation/cursor within the case deadline |
| Capture/restore | 120 seconds | 180 seconds; exact immutable publication/read retries only; do not repeat effects |
| Stop request | 30 seconds | At most two identical requests within 60 seconds; terminal inspection is separate |
| Terminal inspection | 30 seconds | At most two inspections within 60 seconds; missing evidence remains uncertain |
| Reconciliation read | 10 seconds | At most three reads within 30 seconds; no inferred negative outcome |

Schedule-To-Close bounds include queue delay and retries and are clamped to the remaining 600 second case deadline. A Start-To-Close bound never exceeds remaining time. Stop admission when too little time remains for the required safe phase; no deadline forces publication, replacement or destructive cleanup. Cleanup that cannot finish by the case deadline leaves a retained unresolved resource for the owning reconciler; it does not report teardown success. Resource wall time and CPU time are separate limits. Reconciliation after the case uses retained ownership records and requires a separately bounded authorized maintenance invocation. No implicit infinite Activity retry is used.

These choices rely on [Activity timeouts](https://docs.temporal.io/develop/python/activities/timeouts) and [receiver enforced idempotency](https://docs.temporal.io/activity-definition#idempotency). A heartbeat is cancellation/progress evidence, not physical termination proof.

## Strict model request admission

Reuse the existing [offline ledger contract](../../python/claude_agent_sdk/docs/skill-recovery/experiments/budget-policy-proposal.md#implemented-local-storage-contract) and [request admission fixture](../../python/claude_agent_sdk/docs/skill-recovery/experiments/budget_request_offline.py) as reference semantics and test material before adding a component. The fixture already records request digests, serialized cumulative admission and durable receipts; its provider, tokenizer, pricing and supported storage topology are synthetic. The [enforcement disposition](../../python/claude_agent_sdk/docs/skill-recovery/experiments/budget-enforcement-disposition.md#prior-art) explicitly preserves these limits. Do not rerun completed fake batches or promote the fixture into a production executor. The new work is compatible native routing, protected persistent ownership and real provider envelope/accounting qualification, not a replacement ledger framework.

Place the content handling model gateway inside the same approved confidentiality boundary as the native caller. Its privileged component holds the only provider credential and owns outbound inference connections. Generated commands have no provider credential or bypass route. Configure native traffic to the gateway and enforce this through immutable launch configuration and network/process confinement. Environment configuration alone is insufficient. An ordinary outside plaintext proxy would violate the content boundary.

The admission ledger survives execution loss and cannot be rolled back by workspace restoration. It records opaque attempt identity, approved charge profile, reserved request/token/currency quantities and settlement identity. Any outside representation must obey the metadata disclosure policy. Keep request bodies, token content and provider errors protected.

1. Validate the exact model, API path, feature set, request size, maximum output, retry behavior and charge profile before forwarding. Reject unknown or unbounded features and alternate endpoints. Every chargeable attempt, including SDK retries, auxiliary inference and subagent requests, passes this boundary.
2. Compute a pessimistic bound for all admitted billing dimensions: input/context maximum, requested output maximum, permitted cache premiums and any admitted feature fees. An estimated token count or historical usage cannot supply a hard bound. The profile must include a defensible provider charge ceiling and validity interval; if no such bound is available, deny paid admission rather than claim strict prevention. No numeric price or binding provider ceiling is invented here.
3. Atomically reserve one request and the bounded input/output/currency quantities against remaining job authority before sending bytes upstream. Concurrent attempts serialize at this ledger. A retry receives a new attempt reservation even when it is for the same logical native request.
4. Persist `RESERVED`, then transition once to `SENDING` before forwarding. On a crash or timeout after that transition retain the full reservation as potentially spent. Do not automatically replay an uncertain upstream attempt. A proxy restart must reconcile retained state before accepting new traffic.
5. Release unused reservation only using a definitive, authenticated terminal accounting result for that attempt. Missing stream trailers, cancellation or missing usage never refund it. Retain the pessimistic amount when settlement cannot be verified. A result exceeding its admitted bound is a failed provider profile; stop further admission and preserve the incident rather than borrow new authority retroactively.

Strict model usage caps and infrastructure billing are different dimensions. This gateway does not claim to cap cloud resource spending; a selected total-spend guarantee must separately bound every included resource charge or refuse that profile. Protocol qualification remains model free. Any paid run still requires exact prior finite authorization.

Anthropic supports [gateway routing](https://code.claude.com/docs/en/llm-gateway) and publishes a [gateway compatibility contract](https://code.claude.com/docs/en/llm-gateway-protocol). The [token counting documentation](https://platform.claude.com/docs/en/build-with-claude/token-counting) describes an estimate and unsupported request categories. These sources establish integration seams, not a proof of this gateway or a hard billing ceiling. Do not rely on a newer managed setting without qualification against the admitted CLI version.

### First candidate paid API envelope

The first candidate envelope uses the exact model `claude-haiku-4-5-20251001` through the direct Claude Messages API. The [model contract](https://platform.claude.com/docs/en/models/haiku-4-5/overview) records 200,000 context tokens and 64,000 maximum output tokens. The [price schedule](https://platform.claude.com/docs/en/about-claude/pricing) currently lists USD 1 per million base input tokens, USD 5 per million output tokens and up to USD 2 per million cache write tokens. These mutable source observations were read on 2026-10-26; preserve the accepted tariff/limit record and revalidate before paid admission. This is a design candidate, not execution authorization or a changed default model for existing jobs.

Permit text/tool messages, standard service and at most 4,096 requested output tokens. Deny model aliases, fallback to another model, batch/fast/premium service, extended context, nonstandard routing, server tools, image/document inputs, thinking options and any unclassified charged feature. All auxiliary and subagent inference attempts use the same envelope or are refused before forwarding. Local SDK tools and native skills remain runtime operations; they are not provider server tools.

Conservatively reserve 200,000 tokens for each of base input, cache creation and cache read, without assuming their billing categories are disjoint. Price all three at the largest admitted input rate, USD 2 per million, and output at USD 5 per million. Each physical attempt therefore reserves one request, 600,000 input tokens, 4,096 output tokens and USD 1.22048. Use integer microdollars: `3 * 200000 * 2 + 4096 * 5 = 1220480`. Actual usage can be lower; only definitive accounting permits settlement. A job whose remaining authority cannot cover every reservation is refused. Retries consume another reservation; unknown attempts retain theirs.

This bound assumes the supplier enforces its documented token limits and charges only the admitted categories at the accepted tariff. It does not cap a supplier billing error, cloud compute, taxes or unrelated account usage. The authority must state its covered cost dimensions; a requested all-resource bill cap needs a matching resource profile and cannot be advertised from this model-only envelope. Profile admission includes native request-shape compatibility and tariff validation. No live model request is needed to test reservation arithmetic, concurrent refusal or lost accounting; a paid compatibility case still needs separate finite authorization.

## Stopped epoch capture and acceptance

An epoch binds generation, predecessor accepted head, native session identity and the exact package/policy/configuration inventory. The separate native pending-result adapter must preserve original call identity and definitive outcome; its protocol is a dependency, not supplied by SessionStore mirroring or this capture procedure.

1. Before granting an effect, persist its original pending identity and required preeffect accepted state. Independent authority retains admission and uncertainty even if the epoch never becomes accepted.
2. Close input and dispatch admission for this epoch. Drain all admitted native work and every workspace/session/sidecar writer, including children. Complete SDK/store callbacks, close the CLI and obtain evidence that the writer containment is empty. Freezing a running process is not proof of flushed durable state. Any uncontained writer makes capture unsupported.
3. With no writers remaining, validate the complete parseable native records, original typed results and pending classifications, workspace metadata and required sidecars against the epoch inventory. Do not synthesize a missing tool result. Forced termination with missing bookkeeping cannot create a new accepted checkpoint.
4. Capture immutable encrypted objects for the stopped state. Exclude keys, credential files, service sockets and control mounts. Preserve admitted hidden/deleted/executable/link semantics and reject unsupported paths or metadata. Bind the native state and workspace in one manifest with exact object versions, schema and digests.
5. Publish complete object bytes and metadata under immutable identities. For the approved local CheckpointStore, persist files and their containing directories before acknowledgement. Reconcile lost replies against exact original object/envelope identities. Partial objects and orphan manifests are never accepted progress.
6. The Session owner accepts the manifest through a deterministic transition only when the expected predecessor and current generation still match and required object acknowledgements are recorded. Record that transition durably before returning an accepted-state acknowledgement. A lost acknowledgement reconciles that exact head transition; it must not independently advance a latest pointer.
7. Restore only the selected exact accepted manifest into a fresh, initially writer free native epoch. On the same allocated compute, require the prior native/effect writer scopes to be stopped; the trusted supervisor and capture service remain available. For replacement compute, additionally require independent old compute incarnation termination evidence and admission of the new generation. Validate all bound identities, objects and key access before native startup. Any missing accepted bytes is durability failure. Missing required outcome or unsupported pending state parks. A forced stop without a valid new manifest falls back only to the previous accepted head while retaining independent effect uncertainty, never to fresh authority.

Positive child/parallel qualification must include every admitted writer in the drain and outcome inventory. Unsupported crash states park under their original identities. A successful stopped capture does not claim recovery for arbitrary active-process state or serve as positive child recovery proof.

## Rollover, reset and retention

At a handoff boundary, close new input admission, drain message handlers and reconcile pending operation receipts. Carry lineage, original call identities/ordinals, current generation/resource, accepted head, pending decisions, uncertain operations, budget reservations and policy/configuration versions explicitly. Do not carry full transcripts. The same controller and independent authority remain owners across runs; a new Workflow Run ID grants no new effect permission.

The retiring run records its handoff state before Continue-As-New. The successor verifies the carried bindings against retained owners before input/dispatch admission. A crash or lost observation of handoff reconciles the existing chain and identities rather than launching another runtime. Choose no automatic rollover while capture, authority or handler state cannot be classified. A finite prototype may stop before its history bound; claiming supported rollover requires the handoff acceptance cases. Use [Continue-As-New](https://docs.temporal.io/develop/python/workflows/continue-as-new), not a fresh unbound Workflow start.

Retain the approved 24 hour synthetic recovery/reset horizon and minimum seven day object/key/authority retention, extended while any live, parked, reset, replay, handoff or unresolved operation references state. Namespace expiry alone is not a deletion authorization. Janitor deletion requires proof of no remaining reference and completed admitted horizon. Unknown retention denies deletion. Real client retention is separately approved before real data. The [reset procedure](../../python/claude_agent_sdk/docs/skill-recovery/proposals/distributed-recovery/2026-10-08/dsr-0.8-reset.md) preserves lineage and independent authority and distinguishes exact reset history from Continue-As-New. Uncertain Bash remains parked; signed abort only is still an unanswered owner choice. Do not clear authority, fabricate a result or resume through that uncertainty.

## Proposed final confidentiality and release profile

The first final provider candidate follows the existing AWS EC2 direction: NitroTPM instance attestation, an Attestable AMI approved by both parties and independently administered AWS KMS policies. Cloud provider trust is inherited; protection from the cloud provider is not required. This restores the established direction rather than asking for a new platform choice. The approved local container test profile remains a distinct first qualification step. Exact AMI/reference measurements, instance binding, key policies and installed confinement still require engineering selection and qualification.

AWS documents [instance attestation and KMS recipient encryption](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/nitrotpm-attestation.html), [operator isolation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/isolate-data-operators.html), a [sample isolated Attestable AMI](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/build-sample-ami.html) and [attestation document validation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/nitrotpm-attestation-document-validate.html). NitroTPM establishes measured boot/configuration evidence and supports attested key delivery; this is not a claim of SEV-SNP/TDX memory isolation or protection against a malicious cloud hypervisor. Google Confidential Space remains a separately qualified hardware confidentiality alternative, not the default or a new prerequisite.

### Two-party key release and existing envelope

Preserve the approved CheckpointStore version-1 tagged format, AES-256-GCM object encryption, scoped key references, associated data, 96-bit nonce and 128-bit tag. The following is a proposed broker derivation binding behind those existing key references, not a replacement cipher or a claim of independent cryptographic proof. Review it against the exact version-1 schema and admitted cryptography dependency before implementation; reject an incompatible binding rather than silently changing wire interpretation.

1. Each party independently generates a random 32-byte contribution for the job lineage and retains only its contribution under its own KMS authority. Neither KMS policy grants the other party or the workload operator plaintext decryption. Each authority independently approves the exact AMI measurement/configuration and intended job/policy binding. No single administrator may modify both key release policies. Existing data owners can retain their original plaintext inputs; the guarantee concerns the other party's input and combined recovery material.
2. The measured supervisor creates a supported RSA recipient key pair inside the isolated guest; its private key never leaves the supervisor or becomes accessible to generated commands. Each release verifier sends a fresh single-use challenge. Bind the challenge, job/lineage, current generation, immutable incarnation, policy digest and recipient public-key digest into attested signed user data/nonce and the authenticated release request. Validate signature/chain, freshness, exact measurements, recipient binding and the job's independently retained admission before release. PCR equality alone cannot authorize a job or defeat replay. The two verifiers may issue separate challenges/documents for the same recipient. Verify that the admitted tools expose these documented fields before activation.
3. Restrict each KMS decrypt principal to that party's scoped release service; direct guest, client and workload operator calls cannot bypass it. The service forwards the validated recipient attestation so successful KMS decrypt responses are encrypted to that attested public key. Only the admitted supervisor unwraps them. No normal plaintext decrypt fallback is allowed. KMS does not validate the application's nonce or user-data protocol, so the service enforces challenge freshness, recipient and retained job/generation admission before every release. Failure or refusal by either authority releases no combined key and does not trigger a substitute contribution. Administrative policy changes remain outside the workload operator's role and require that party's explicit authorization.
4. In the supervisor, derive a 32-byte lineage root with HKDF-SHA256 Extract-and-Expand over the ordered, length-framed pair of contributions. Use a retained random 32-byte public salt and domain-separated canonical `info` binding protocol version, party ordering/identities, job, lineage and admitted policy. Use fixed-width unsigned lengths for every framed field and reject duplicate/missing party identity. The salt and derivation metadata belong to an immutable broker record referenced by the existing key reference. Generation is checked at release, but is not an input that makes earlier accepted objects undecryptable after replacement.
5. Derive each 32-byte object key with a separate HKDF-SHA256 domain and an immutable broker-assigned object/envelope key identity. Bind exact object/version/schema scope in the existing authenticated associated data. Reserve each encryption key identity durably before encryption and consume it for one encryption. Retry by replaying the exact retained ciphertext envelope; if that envelope was lost, allocate a new key identity before encrypting again. Never reuse a key/nonce pair, including after process loss or restore. This allocation state is outside restored workspace files. Preserve exact ciphertext/envelope digests for publication reconciliation.
6. Retain both encrypted contributions, salt/derivation records, policy versions and all referenced key identities through every supported recovery horizon. Authorized replacement obtains both contributions under fresh generation/incarnation challenges and derives the same old object keys. Missing contribution, revoked access or absent key metadata blocks restoration; it never becomes an empty new session. Erase unneeded in-memory contributions and derived keys when stopping the supervisor. Guest memory erasure and process isolation require implementation verification.

[RFC 5869](https://www.rfc-editor.org/rfc/rfc5869) defines the HKDF building block. The [cryptography AEAD contract](https://cryptography.io/en/latest/hazmat/primitives/aead/) defines authenticated encryption and nonce reuse constraints. Neither source proves this composed key release protocol. Qualification must include independent policy administration, forged/stale challenges, wrong image/job/incarnation, substituted recipient keys, missing party contribution, repeated encryption allocation and exact old-object recovery.

Use a production attested image with no operator shell/debugger, plaintext content logs, arbitrary launch overrides or plaintext snapshots. Reject wrong image, debug state, wrong job, stale generation and unauthorized key release. Model credentials are scoped to the inside gateway. Ordinary Claude inference receives authorized plaintext model inputs; acceptance of that provider access is an explicit remaining owner choice, not confidential inference.

The proposed default release policy denies freeform questions, freeform reports, raw trajectories, source excerpts, native arguments and diagnostics. The synthetic qualification report contains only opaque `job_id`, `policy_version`, finite `state` (`PASSED`, `FAILED`, `PARKED`) and a bounded array of registered check identifiers with finite outcome codes. It contains no protected source, tool arguments, paths or arbitrary text. Status and check values are intentionally permitted information only if this policy is accepted; schemas alone cannot prove semantic nonleakage.

Additional registered domain reports and client fact questions require a jointly approved versioned declassification policy defining recipients, allowed fields/functions, bounds and authentication. Native output is untrusted input to that policy gate. Neither a model assertion nor a secret scanning classifier authorizes release. Until accepted, keep output protected. The qualification report does not replace the retained useful domain report requirement.

Business report schemas are supplied by registered jobs, not invented by the runtime integration. The runtime requires a `ReleasePolicy` binding policy/schema version, executable validator/serializer digest, authenticated recipient and recipient encryption key, allowed output class, byte limit, job/lineage and required party approvals. It runs that policy inside the protected boundary before encrypting the released artifact to the admitted recipient key. A release operation binds the accepted artifact digest, policy digest and original operation identity; duplicate delivery returns the same encrypted artifact reference. Missing policy, invalid recipient, unaccepted source artifact or validation failure refuses release without a content bearing diagnostic.

The runtime contract is testable with a synthetic registered policy that permits a fixed harmless marker and rejects protected canaries, forged recipients, changed policy digests and replayed operations. This proves policy invocation and boundary enforcement, not semantic safety of arbitrary future customer policies. Every real job must supply its approved policy before protected input or key admission. Questions are disabled unless the job additionally admits an authenticated question/answer policy. Selecting a particular assessment report schema is outside this runtime extension and is not a prerequisite for its implementation or design review.

## Remaining design and acceptance gates

This candidate is ready for bounded adversarial review, not activation. The proposed main-agent recovery, concrete paid envelope and two-party key binding need review at their stated scope; the unidentified active-child recovery mechanism remains a full outcome design gap. The inherited trusted cloud provider and AWS first direction are not reopened decisions. Business report schemas are job inputs, while the runtime must enforce their authenticated release contract. Required later before runtime claims: implementation and fault injection for concurrent identity handling, capture/publication crash windows, stale generation, restored uncertainty, credential bypass, charge reservations, key release and permitted output. Each real job still needs its actual input, model access, key and release authorizations. Existing source inspection and old qualification do not close these new cases.
