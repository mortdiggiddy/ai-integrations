## Conclusion

The discovery contains a viable proposed cold recovery recipe, but no qualified external storage deployment yet. It does not presently meet every High, Medium and Low outcome in issue 31. Its explicit unsupported child denial and serial pending limitation cannot count as satisfying durable subagents or parallel calls. User intent now requires tracking those positive outcomes as proposed expansion work, with adoption and safety gates, rather than describing exclusion as resolution.

The strongest route is accepted immutable trajectory and workspace references in Temporal, independently durable component storage, exact original pending SDK recovery, protected dispatch admission independent of workspace rollback, and independently established termination before replacement. Existing product primitives support each part. The combined host loss and partition behavior has not been demonstrated. VM memory snapshots are optional acceleration, not required conversation durability or an effect ledger.

## External storage answer and next qualification

External payload storage, Claude SessionStore, workspace bytes and protected effect admission are four different contracts. Temporal's external payload facility can reduce history size, but it cannot snapshot arbitrary container files or kill old processes. The proposed recipe stores immutable trajectory and workspace components, publishes one matching manifest after durable acknowledgements, accepts that reference in history, then permits exact original pending recovery only after protected ownership and old termination. Orphan uploads do not dispatch; missing accepted bytes park. Storage errors may fail and retry the entire task, so the effect admission record must survive that retry independently.

The recipe is viable as a testable proposal, not solved as a deployed product. Needed proof includes actual chosen backend driver/retention/encryption/key access; restore after host destruction; snapshot publication gaps; exact native metadata; live partition witness; old guest provider/power fencing; rollback independent effect intent; and source-pinned allowed/denied continuation. Current local/container tests cannot establish cross-host or cloud provider guarantees.

Recommended additional vectors: kill a Docker sandbox before its exit snapshot is acknowledged; race two mounts that write different accepted generations; attempt takeover while E2B pause was refused; treat an S3 FUSE mount as claim storage and require refusal if conditional/flush semantics are unproved; restore a stale authenticated confidential bundle against a newer independent accepted head. These are preparation vectors only. Complete issue coverage should assign each vector to the existing storage/compatibility owner or an explicit proposed expansion decision without marking criteria DONE.
