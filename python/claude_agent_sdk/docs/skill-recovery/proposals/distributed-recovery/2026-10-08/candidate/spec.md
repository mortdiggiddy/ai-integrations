## Objective

A logical validated Skill run resumes its exact accepted Claude pending call/result in a fresh compatible environment after supported failures, preserving acknowledged state and refusing ambiguous effects.

## Background

The recommended qualification recipe is Temporal accepted orchestration and bounded checkpoint references, exact immutable trajectory blobs and workspace bundles in independently durable storage, the existing Claude SDK original pending recovery adapter, and independent dispatch authority with verified old execution termination. Durable workspace reattachment and bounded full trajectory in history remain comparison alternatives. These are proposed compositions of existing primitives, not a new executor or implemented distributed guarantee. Phase 1 supplies bounded original pending recovery and scoped policy evidence; distributed host loss, storage and production signing/isolation remain unproved (EV-12/EV-32/EV-33/EV-34).

The reference policy Workflow currently refuses unavailable production execution rather than implementing this application effect path. Later authorized work must integrate that seam, not build another executor. The existing runner requires conditional session append for original pending recovery and assigns workspace/outcome/ownership checks to its caller (EV-11). Checkpoint readback already exists; durable backend acknowledgement is a distinct requirement.

## Goals

Preserve each accepted boundary within the selected fault model. Recover original serial pending results without repeated effects after verified prior termination. Expose safe parking as a supported outcome. Qualify engine/package/policy compatibility explicitly. Attach falsifiable tests to every promise before advertising it. Optional Mods may improve observation or native result projection within this architecture; exploratory complete model-response escrow is a separately offered future contract, not a new guarantee of this candidate.

## Non-goals

Arbitrary external exactly once execution, every streamed token or live socket, unsupported child recovery, expiry based ownership takeover, claim release/redo, silent upgrades, and recovery after loss or undetectable rollback of all independent authorities are excluded. VM memory restoration is not required. Confidential execution is optional pending BD-5.

Discovery does not authorize implementation, infrastructure setup, live models, installation, image operations, contact, commits or publication. No new runtime proof follows.

## Scenarios

After a destroyed container, independent state survives; a replacement verifies accepted receipt, old termination and all identities before exact pending recovery. After an unreachable host, the run parks while old code might still reach storage or effects. A timeout cannot release ownership.

After a remote effect succeeds but its result is lost, claims and independent intent prohibit redispatch; Bash parks without model facing fabricated unknown result. After a preclaim volume restore, independent intent still marks that ordinal uncertain, even if generation is unchanged.

An answer accepted during compute failure survives as one exact durable decision; replacement applies it to the original pending question only after validated teardown/state. Cancellation, conflicting or late answers refuse.

## Rigor tier

Proposed spec anchored, pending BD-6. Effect/security contracts and retained histories have high switching cost. Adoption includes automated contract enforcement and source-sync-reconcile registration. No code generation or execute-design follows.

## Constitution

### INV-1 Failure model

Each proposed ordinary Activity sets finite Start-To-Close and Schedule-To-Close bounds, explicit retries and bounded heartbeat progress for long work. Numeric queue/execution/shutdown deadlines come from BD-4 before M2. Safe idempotent preparation/read/reconciliation may retry finitely. Bash and special nonrepeatable Edit use one attempt. The selected original pending recovery route rejects Activity attempts other than one and forked resume; its segment Activity therefore uses maximum_attempts=1 and automatic retry parks/refuses. A proposed new orchestrated first attempt must retain original identity and obtain separately tested admission/termination/state reconciliation, never bypass this guard through Reset or a fresh lineage. Postintent ambiguity parks without another segment.

Container/pod/Worker/host failure ordinarily replays the same Workflow Execution and RunId on a compatible Worker; Activity retry changes its attempt, not the Workflow RunId. Continue-As-New deliberately starts a new RunId with the same WorkflowId. Workflow retry and Reset are separate execution operations, not placement failover. Keep logical session/effect identity distinct from engine session, execution RunId, attempt and runtime instance. Open Workflow ID conflict policy and retained closed ID reuse policy govern orchestration admission, not live subprocess exclusivity. Reject Duplicate is retention bounded, not a perpetual tombstone (EV-32/EV-37/EV-40).

The initial recommended fault scope covers execution host loss with Temporal Service and storage outside that host, and parks on host reachability loss until independent termination is established. Temporal Service regional loss, forced Namespace failover or rollback of service history is a separate fault domain and guarantee requiring BD-1/BD-2/BD-3 qualification. Namespace availability does not imply workspace availability or stale host death.

Cancellation requests whole environment teardown, preserves uncertain claims/intent and takes precedence over answer/resume. There is no generic compensation for arbitrary Bash; business compensation needs separate specification. Heartbeats supply progress/cancellation communication, not proof an unreachable process stopped (EV-14, https://docs.temporal.io/design-patterns/long-running-activity). Proposed enforcement is A-60 through A-64.

If an optional Mods lane is adopted with a required bridge, its hooks remain fail-open in the pinned source: throw, own-time overrun, malformed output or catch failure can pass execution beneath them (EV-19/EV-24/EV-26). A second Mod is insufficient as the sole preventive control. Independently constrain native calls and direct plugin process/fs/http/MCP effects. Missing required hooks after startup, reload, worker respawn or policy change must refuse/park through the independent controller before unsafe effect/pending continuation. A selected escrow promise additionally requires independent model/provider prevention before accepted-response recovery or another request; observation alone does not require a new model gate. Missing observation-only hooks may reduce telemetry if baseline controls remain complete. These are proposed integration obligations A-71/A-72/A-74, not source-provided enforcement. Own hook work has 10-second budget, catch grace 1 second, lingering abort work 5 seconds; $/next waits are generally excluded except clock waits. These are not provider spend, wall-clock or storage deadlines.

### INV-2 Worker and task queue topology

New proposed roles are deterministic Workflow control Workers, segment Workers invoking the existing SDK runner, trusted effect wrappers launching confined effects and supervisor/lifecycle Workers. Queue names and fleet sizes are not existing application facts. Segment/effect queues are separate concerns; every compatible Worker uses qualified storage and identical canonical cwd without affinity. Sequential exclusive volume attachment is an optional specialization pending BD-2/M2, not silently shared mounting.

Use retained compatible versioned Worker deployments, qualified package/policy/SDK/CLI/image/hook/executor fingerprints and explicit rollout/drain/replay/migration tests (EV-15, https://docs.temporal.io/worker-versioning#inheritance-semantics). Pinned identity is not SDK compatibility proof. Runtime, service and exact deployment pins are BD-2 choices; Kata/Kubernetes/Ceph/Docker are candidates (EV-3/EV-4). Python Worker roles follow EV-10; A-67 gates resume compatibility.

### INV-3 Workflow and activity modeling

Workflow code is deterministic orchestration using SDK safe time/identity APIs; model, filesystem, database, package verification and runtime IO are Activities (EV-5/EV-10, https://docs.temporal.io/workflow-definition#deterministic-constraints). Replay consumes accepted results without launching Claude. The policy refusal seam remains until authorized integration and qualification (EV-17).

Proposed states are PREPARING, SEGMENT_OWNED, SEALED_CANDIDATE, ACCEPTED_PENDING, EFFECT_INTENT, EFFECT_RUNNING, OUTCOME_RECORDED, RECOVERY_READY, WAITING, PARKED and TERMINAL. These are unimplemented application contracts. ACCEPTED_PENDING alone never authorizes dispatch: accepted history, sealed consistent state, current protected authority and prior termination are all required. Queries/Search Attributes are discovery, not execution authority.

### INV-4 Long running behavior

Continue-As-New carries bounded accepted references, decisions and unapplied answers, lineage/ordinal and park state after handlers finish (EV-6, https://docs.temporal.io/develop/python/workflows/continue-as-new; EV-16, https://docs.temporal.io/handling-messages#message-handler-patterns). It never resets effect identity, clears claims or forgets unresolved ownership. Wait/park handover has no uncontained active execution. Updates racing handover are visibly accepted or rejected; application deduplication survives new Run IDs and is not replaced by per-run Update ID deduplication. The recommended lane stores raw trajectory/workspace/output externally; bounded exact delta history is a comparison lane subject to payload/history and handover limits. Reanchor or retain every referenced earlier object throughout live/reset/replay windows; a new run retaining an old reference cannot assume expiry is safe. History/payload thresholds, wake periods and segment caps are BD-4 choices tested at M4, not invented production defaults (A-66/A-68/A-69, EV-32/EV-38).

### INV-5 State ownership and idempotency

Workflow history owns accepted orchestration, decisions and a bounded head/receipt binding exact trajectory and workspace identities. Recommended trajectory authority is immutable opaque chunks in durable object storage, using qualified SDK External Storage/claim check where suitable, with accepted head/parent/digest in history. Bounded exact transcript deltas returned as Activity outputs and reconstructed in Workflow state are a comparison lane; a transactional shared SessionStore is another qualified alternative. A Query only reads existing state and records no transcript; accepted Activity outputs or messages supply its durable inputs (EV-32/EV-35/EV-38/EV-41). External Storage is Public Preview and does not snapshot a filesystem, guarantee object retention or transact with Temporal. No SDK upgrade or adapter installation follows from choosing it as prior art.

Each lane preserves exact opaque entry order, conflicting UUID refusal, expected accepted head and typed original pending call/result. The existing SDK adapter must materialize/load and conditionally append that exact accepted prefix/result; a blob reference or summary cannot bypass its guard. Durable storage acknowledgement and readback must precede candidate receipt acceptance (A-60). SDK mirror writes alone cannot satisfy the barrier. Missing/corrupted accepted data, stale head, conflict or mirror failure refuses acceptance/recovery, with no fresh/local session fallback. Workflow serial head acceptance plus immutable chunks may satisfy the authority without a separate transactional transcript database, but the selected composition remains unqualified.

Trajectory, workspace and dispatch authority are distinct consistency/rollback roles, not a demand for three products or databases. A qualified object store may hold separately bound trajectory and workspace blobs. The independent Entity Workflow can own dispatch outside outer session Reset. Common failure domains, retention, authorization and cross-component receipt consistency still require proof; separation by directory name alone supplies none.

Two workspace lanes are proposed: restore an immutable accepted bundle into a fresh confined local workspace, recommended for the first comparison target, or reattach an independently durable filesystem. The running guest still uses a qualified local/POSIX interface and admitted canonical cwd; object storage is not mounted and assumed equivalent. Bundle receipts bind files, deletions/hidden state, content digests, executable/mode bits, permitted ownership, symlinks/hard links, required attributes and external mount declarations. Restore rejects traversal, escaping links, unexpected devices and writable protected aliases before SDK startup. Keep immutable package separate/read only. Quiesce all writers before sealing, then verify exact pre/postimages and native Write/Edit bookkeeping (EV-33). Confidentiality and integrity do not alone establish freshness.

The canonical v1 shared-volume and protected file-claim contract remains implementation authority until BD-6 adopts a tested extension. The copied candidate permits qualified cold restore or reattachment; neither weakens required protected spawn admission. Scripts write only work/. Where retained file claims guard spawn, the trusted wrapper creates ordinal and key claims with qualified exclusive create and durable sync; partial/uncertain creation parks (A-61). Missing protected authorities are not recreated as new execution. A missing local materialization can only be rebuilt from validated accepted immutable state after ownership admission, never by guessing an empty lineage.

Proposed extension A-62 records independently durable dispatch intent before Bash claims/spawn. Intent binds namespace/logical lineage/original ordinal/key/input digest/accepted checkpoint/versions and is atomically unique; key excludes current RunId and Activity attempt. Its authority sits outside workspace rollback and outer session Reset. Retain protected wrapper/file spawn guards while qualifying the composition. Two candidate authorities are a separately retained Entity Workflow owning the one effect Activity scheduling decision, or a protected unique transactional SQL/equivalent store. Both are application protocols, not another executor or implemented guarantees (EV-34/EV-39).

In the Entity Workflow alternative, duplicate requests return status or exact known outcome, never a reusable permission-to-spawn reply. The ledger validates independently accepted segment receipt and queues the original existing effect wrapper once with maximum_attempts=1; no caller spawns because a repeated Update returned its prior successful reply. The ledger must not be reset, recreated, expired or restored behind outstanding effects within the supported recovery window. Outer Reset consults it. Its Continue-As-New carries claims, tombstones and dedup state, and waits for handlers. Child deployment requires explicit independent lifecycle/confirmed start; a separately started entity is the preferred qualification target. Missing/regressed authority refuses rather than automatically starting a replacement ledger (EV-34).

For effects whose receiving service atomically enforces an idempotency key with its mutation/result, use that standard pattern; a same-database SQL transaction is concrete prior art. A transactional outbox retains intent but its receiver still needs idempotency. Arbitrary Bash has no generic transaction with either Temporal or SQL: intent-before-spawn can conservatively prevent redispatch but may park even when no effect happened. RunId plus ActivityId protects retries within one run only; logical intent identity must survive permitted new runs/reset. Saga compensation is separately specified business recovery, not proof of no duplicate shell effect (EV-32/EV-34/EV-39).

Any existing or uncertain intent without a complete exact authoritative outcome and matching durable postimages parks, even if no spawn was observed. No intent release or fresh ordinal/lineage escape exists. Reset consults original lineage intent even when Activity attempt returns to one. Independent durability also requires rollback protection: deployment must provide an externally checked monotonic incarnation/anchor or a nonrollback restore contract for the chosen fault model. Lost, missing or regressed authority refuses as unrecoverable; simultaneous undetectable rollback of every authority is excluded. Auto recreation is forbidden.

Ownership epochs serialize admission but do not stop old processes. Supervisor supplies authoritative old termination; API object deletion, attachment release, TTL or brief canary silence alone is insufficient (A-64). Confirmed death cannot prove a remote service rejected an earlier request.

Ordered commit protocol:
1. Prepare verifies logical lineage, admitted versions, current independent intent/claims, accepted trajectory/workspace identity and prior termination; admit one owner. Restore a cold local bundle or reattach the qualified volume only under that admission.
2. SDK defers effects. Drain session mutations and workspace writers, then terminate owned execution. Durably persist exact transcript prefix/pending identity and quiescent workspace bundle/inventory, then seal one immutable manifest binding every digest, accepted predecessor, pending identity, versions and cleanup identity. No accepted mutable suffix is assumed safe.
3. Return candidate receipt. Only committed Workflow Activity completion accepts it. An orphan candidate cannot dispatch an effect.
4. Revalidate accepted receipt/termination/state. Admit independent Bash intent through the qualified ledger/unique store, schedule the existing wrapper once under its protected spawn guard, and persist required claims before spawn. A duplicate submission returns status/outcome without another scheduling/permit. Any uncertainty parks.
5. Durably persist exact known outcome/postimages. If Activity completion is lost, this is an orphan completion. Adoption requires exact accepted dispatch, intent/claims, result JSON/type and postimage validation with no contradictory record; otherwise park. Never repeat an effect to learn its outcome.
6. After effect teardown, original pending adapter conditionally appends exact result at expected head; interrupted append reconciles same identity. Startup refuses malformed identity, changed head, unsupported children or mismatches.
7. Janitor retains live, idle, parked and uncertain state; closed records remain through all allowed reset/replay windows.

Optional Mods do not reorder steps 1-7 or authorize an effect before step 3's accepted sealed receipt. Holding a call or calling a durable bridge from inside a live hook is not acceptance; a synchronous hook-to-effect Activity is rejected as a drop-in executor. Returning deny settles an error and cannot establish unresolved original pending recovery. Catch replay-safe next is dispatch-local, not crash replay, and returning deny after execution cannot undo it. Exact original pending state and verified stopped ownership remain necessary even when the Mod supplies native result projection (A-73, EV-19/EV-25/EV-26).

No transaction spans workspace/object storage, optional database and Temporal. Every intermediate write gap reconciles or parks; only validated sealed receipts advance acceptance (A-63). Upload-before-history acceptance is an orphan without dispatch authority; accepted manifest with missing component refuses/parks and fails promised acknowledged-state preservation under its selected fault model. Canonical ordinary Write/Edit repeatability and special overlap rules remain required; actual native restore differential tests retire their inherited premises. An independent termination receipt does not retract a remote request issued before death; reconcile its definitive result or retain uncertainty.

### INV-6 Observability and service levels

SDK Worker and service/Cloud metrics are separate when applicable (EV-7, https://docs.temporal.io/develop/worker-performance/metrics). Application metrics cover queue wait, attempts, receipt/state refusal, mirror failure, park cause/age, ownership uncertainty, cleanup latency, restore latency and duplicate effect violations. Logs/traces use opaque identities without content leakage; identifiers do not become metric labels. Replay safe counters require proof.

BD-4 gates numeric recovery time, accepted progress loss/fault scope, availability, concurrency and payload/history targets. Each measurable objective needs a threshold, window and alert for queue delay, recovery, cleanup, parked age and storage acknowledgement. Zero unsafe replacement/duplicate observations are test safety oracles, not an invented availability SLO. M4 measures targets/alerts (A-69).

### INV-7 Security and privacy

Sensitive prompts, questions, answers, tool inputs/results and references use explicit payload codec and tested failure conversion. Search Attributes contain only approved nonsecret discovery metadata; failure text/stack leakage is excluded or explicitly converted. Payload encryption is not automatic (EV-8/EV-13, https://docs.temporal.io/evaluate/features/data-encryption).

Trusted governance Mod admission is unresolved: current validated-package runner uses project setting sources, plugins=[], controlled Skill inventory and disableSkillShellExecution (EV-11/EV-28). Keep arbitrary plugin/bundled Skill and unsupported child denial. A selected managed/prepend bridge must prove actual SDK admission without widening package loading. Official sec-default is a scoped managed policy reference, not universal mediation: its seating/options can change and it passes direct process/filesystem/HTTP/MCP/model events. Runtime type/chain/package identity and independent capability policy must be checked at each authority transition, not only startup (A-71/A-72, EV-21/EV-22).

Controller/gateway/key authority stays outside untrusted effects. Effects get necessary package read only and work/ writable, with no session/intent/claims, Worker credentials, supervisor socket or service account token. Mounts have no writable alias. Separate identity/guest/container, restricted proc/egress and whole descendant containment require BD-2/M4 proof (A-65). Namespace/history/session/key retention and reset policy are BD-3; unknown horizon forbids intent/claim deletion.

BD-5 selects trusted versus malicious host requirements. Optional confidential lane needs selected TEE, attestation policy, key release/freshness, encrypted storage and rollback proof. Attestation or key release does not revoke an old guest or atomically execute external effects (A-70/EV-13). It cannot silently replace termination/state authority.

## Alternatives considered

Recommend fresh sandbox from accepted exact application state, with Temporal owning accepted head and immutable trajectory/workspace blobs as the scalable qualification target. Compare bounded trajectory delta history against claim check rather than forcing a separate transcript database. Compare independent Entity Workflow scheduling authority against protected unique SQL admission rather than assuming SQL is mandatory. These recommendations are proposed mechanisms pending BD-2/BD-3/BD-6 and tests, not owner answers (EV-32/EV-34).

Compare cold immutable workspace restoration with durable reattachment. Managed Docker exclusive volumes reduce writer coordination but require provider host-loss durability/termination and attachment specialization proof (EV-3/EV-33). Docker local volumes address surviving-host container loss only; microVM snapshot memory/disk packaging, reusable clones, network state and confidential key freshness do not supply accepted checkpoint atomicity or terminal ownership. Kata/Ceph exposes host/storage faults at greater operational cost (EV-4). FileSessionStore on a network mount and SQLite proof on a shared mount remain rejected as assumed production stores (EV-2); a selected tested adapter is a distinct qualification.

VM memory authority adds disk/socket/secret/active clone hazards and is rejected as initial requirement. Confidential runtime is optional threat protection, not durability (EV-13). A narrower same host deployment cannot advertise permanent host loss. Timeout/TTL/force deletion is rejected as sole failover authority.
