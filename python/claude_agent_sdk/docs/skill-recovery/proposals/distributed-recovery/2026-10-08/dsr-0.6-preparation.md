## Recommendation and smallest decision

Subsequent source reconciliation (2026-10-09): [the maintained Issue 31 proof map](priority-sweep/coverage.md#october-9-release-check-reconciliation) owns the public pinned native port, corrected latency/nonexecution claims and observed plugin CI cells. These strengthen a selective reuse comparison but explicitly leave workspace failover open. This prepared deployment recommendation, owner-decision split and physical proof boundaries are unchanged; the earlier independent review remains evidence for its original scope.

Recommend retaining canonical version 1 for the next stage. Select a Linux POSIX shared network filesystem class, with NFSv4 as the first qualification target, mounted at the same absolute deployment path by every segment and effect Worker. Choose the two real mount qualification rig rather than asserting tested cross host semantics. A backend product, version, mount options and storage failure domain must be recorded before that rig executes; the protocol name alone proves none of its required semantics. A same-host volume is a useful preliminary control, not a substitute for the selected network class.

Required semantics remain common numeric user/group mapping across hosts, POSIX path/mode/rename behavior, close to open read visibility, protected `O_CREAT | O_EXCL | O_NOFOLLOW` claim creation and preservation of acknowledged files/claims through the declared fault domain. Qualify durable acknowledgement and mount/cache behavior rather than assuming a successful local write is durable everywhere. The network filesystem recommendation reflects contract fit, not demonstrated superiority over cold restoration.

Choose an unprivileged effect container with a separate PID namespace, restricted `/proc`, no privileged mode, host runtime socket or Worker credentials, protected read only package paths and only `work/` writable. A trusted supervisor outside effect control must identify the exact container incarnation and contain and observe the complete descendant set. Default deny egress; any permitted destination and secret must be explicit. Container separation is a qualification target, not an assertion that a stock container prevents every escape or is suitable for hostile tenants. The segment SDK session also remains under the existing trusted ownership/cleanup barrier.

Deferring confidential hardware does not waive baseline sensitive-storage/payload encryption, least privilege or protected credentials/package/claims. Canonical security and DSR-0.11 retain those requirements; this bounded choice assumes a trusted host and supervisor rather than claiming protection from a malicious host.

This retains the existing runner, mandatory SDK entrypoint, protected ordinal/key file claims and accepted segment before effect placement. It does not adopt an Entity Workflow, new transcript authority, cold bundle protocol, new Mods lane or runtime version. Implementing DSR-2.1 still requires approval of the applicable DSR-0.6 choices and a named Security role holder. Physical effects and cross host failover remain gated by their later proof tickets even after workspace construction is allowed.

The smallest operator decision is whether to select this bounded canonical qualification target, with permanent host loss and partition takeover parked pending separate proof. The Security and deployment/storage role holders must then be named for the decision record; no person is silently assigned here. Approval of that target alone is neither distributed proposal adoption nor permission to execute a rig, provision storage or run a model.

For the later distributed target, retain [storage synthesis](storage-loop/synthesis.md)'s preferred cold restore comparison: accepted Temporal head, immutable exact trajectory/workspace receipts, a qualified original pending materializer, independently retained dispatch authority and independent termination. This addresses permanent execution-host loss more directly than host-local volumes, but changes the canonical storage/authority contract and requires a separate BD-6 decision. Do not implement that recipe through DSR-2.1 under a volume-class approval.

### Ordered acceptance boundaries

The following are proposed adapter obligations derived from the canonical accepted-segment, original pending/result and workspace requirements. They prescribe observable outcomes, not new public types or an adopted receipt schema. Filesystem, publication and process inspection belong outside Workflow code; the Workflow accepts bounded references and validated observations. No transaction across Temporal, a conversation store and a filesystem is claimed.

| Boundary | Required ordering and identity | Refusal and qualification obligation |
|---|---|---|
| Segment returns an original pending call | Preserve the exact native conversation/pending records and identify the matching pre-effect workspace, immutable package, policy/runtime and lineage. The accepted segment and stored logical call identity must precede external effect dispatch. A checkpoint failure must not permit dispatch. | Conversation present with absent, mismatched or unacknowledged required workspace state refuses. A check that only runs after the tool step cannot satisfy the pre-effect boundary. |
| Governed effect admission | Validate the accepted pending call and admitted workspace before the existing claimed effect path can run. Preserve the stored lineage/ordinal/key and both protected claims. A snapshot/reference alone never supplies spawn permission. | A retained claim, partial pair, unknown outcome or uncertain ownership cannot be erased or bypassed by restoring an older workspace. Reuse the canonical ordered outcome table, including its narrow affirmative NotStarted classification. |
| Effect returns a definitive original result | Preserve the exact native result and required postimage under the same original identity before accepting completion for continuation. Quiesce all relevant writers for any sealed image; exclude effect control over protected state. Record the accepted pairing rather than choosing the most recently uploaded object. | Mutation followed by lost result/postimage publication or ACK stays unresolved until the same identity is reconciled. Do not rerun Bash to reconstruct output or accept a result paired with pre-effect files. |
| Replacement or next segment admission | Validate the currently accepted conversation/workspace/result pairing and package/policy/runtime. Replacement requires authoritative exact-incarnation cleanup of the old SDK/effect execution and descendants before any replacement invocation. The next segment cannot pass while an effect remains ambiguous. | A reachable store, lower or unchanged generation, timeout, cancellation acknowledgement, lease expiry or force deletion supplies no missing physical proof. A safe refusal for lost accepted bytes is still durability qualification failure. |
| Uncertain-effect policy | The governed profile requires park for ambiguous Bash before generic failure-to-tool-result conversion. Persist the original pending identity and park reason; dispatch no further effect and start no model segment. Upstream's tell-Claude behavior is an alternative generic mode, not the governed default. | Human acknowledgement or an approval to continue is not affirmative nonexecution evidence. Use existing authenticated decision/reconciliation controls; retain exact result plus required postimage and cleanup before recovery, otherwise remain parked or cancel. Do not mint a fresh call identity as recovery. |

For the canonical shared volume, missing or corrupt accepted state refuses rather than restoring an older pre-effect image. Any repair remains within DSR-4.2 and must preserve unresolved claims and outcomes. For a separately adopted immutable publication route, published-but-unaccepted objects remain orphans and must not replace the accepted pairing. Duplicate identical publication may reconcile the original digest; changed bytes at the same identity refuse. These rules do not select external conversation storage, a cold bundle format or independent dispatch authority.

No cross store transaction is claimed. An uploaded but unaccepted object is an orphan, not dispatch authority. An accepted object that is missing or corrupt requires refusal and is a durability qualification failure, even when refusal preserves safety. Cleanup must not erase the sole readable stopped workspace before its required sealed publication. A local generation counter detects some stale restores; unchanged generation does not prove fresh claims or files.

The recorded Entity Workflow/Update and Activity completion patterns are partial precedent for this composition, not sanctioned arbitrary Bash exactly once. Receiving-service idempotency and same-database key/mutation transactions apply only to effects that actually supply those contracts. No idempotent receiver is invented for general Bash. Retained workflow admission and one Activity attempt do not confer permanent uniqueness or physical termination.
