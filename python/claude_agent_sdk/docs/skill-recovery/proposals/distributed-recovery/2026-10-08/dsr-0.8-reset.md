# DSR-0.8 reset detection and operator procedure

Status: PARTIAL (2026-10-14). Detection, lineage ownership and the procedure are specified for review. The uncertain Bash action policy needs the operator's answer. DSR-3.3 and DSR-3.5 own implementation and execution proof. This record grants no reset or runtime authority.

## Authority and identity

The [canonical component contract](../../../spec.md#selected-component-boundaries-2026-10-12) remains authoritative: the Session Workflow owns the accepted head; the protected Entity owns nonrepeatable scheduling; the independent controller owns exact-incarnation lifecycle; storage preserves exact acknowledged bytes. This record owns the reset procedure, not a second dispatch or storage contract.

The project maintainer implements the trusted application starter through the governed gateway. Before the first Workflow start, the starter generates a random lineage UUID outside Workflow code and conditionally reserves its namespace, application job identity, Workflow ID and immutable start-input digest in protected admission state. UUID randomness alone does not enforce uniqueness. A collision or conflicting binding refuses start. A lost start reply reconciles the same reservation and exact execution; it must not mint another lineage. A genuinely new job, including permitted Workflow ID reuse after closure, needs a fresh lineage and reservation. Keep old bindings and tombstones through all referenced recovery horizons.

The starter supplies the lineage in immutable Workflow input. Reset to the first Workflow Task reuses that input; Continue-As-New carries the same lineage explicitly with ordinal, original call identity, accepted references, decisions and park state. Missing lineage is an admission refusal, with no Workflow-generated fallback in the new governed profile. Historical runs need an explicit qualified migration; this does not change their identity silently. DSR-2.1 prepares this input contract; DSR-3.5 proves first-task reset and uniqueness negatives. Do not infer identity safety from the SDK's deterministic UUID seed.

## Concrete reset detection

Use a trusted gateway/controller history probe outside Workflow code before execution admission or replacement. Fetch history for the exact namespace, Workflow ID and current Run ID, never the latest execution by Workflow ID alone. Bind the returned execution and start input to the reserved lineage and current protected authority. Read the start event's `original_execution_run_id` and the server reset marker. Record source event IDs and digests with the observed Run ID. A stored claim's Run ID is diagnostic only.

| Classification | Required evidence | Admission consequence |
|---|---|---|
| Reset | The current Run ID differs from the start event's nonempty `original_execution_run_id`, and the new branch contains `WorkflowTaskFailed` with cause `RESET_WORKFLOW`, matching `new_run_id` and a retained `base_run_id` | Hold execution for the ordered procedure below; reconcile protected authority using original identities |
| Continue-As-New | The current start has its own original Run ID; `continued_execution_run_id` names the predecessor, whose `WorkflowExecutionContinuedAsNew` names this `new_execution_run_id`; carried input/lineage and authority match | Apply the normal qualified handover barriers; no reset inference from older claim Run IDs |
| Initial start | Start original Run ID equals current Run ID, no predecessor transition, and the exact starter reservation matches | Apply normal initial admission |
| Retry, cron, unavailable or conflicting history | A different initiator/transition, absent fields, mismatched marker, unavailable predecessor or conflicting input/authority | Refuse the unsupported transition or park as `transition_unverified`; no guessed Continue-As-New or fresh authority |

A Continue-As-New after an earlier reset has a new start event. Its immediate transition can be Continue-As-New while the lineage retains the earlier reset investigation and park. Scan the current branch for the reset marker that names the current Run ID, not an inherited earlier marker. Repeated resets bind the latest branch/base relationship and retain earlier observations. Reset to an old run must reconcile all later admitted ordinals and accepted heads in independent authority, not only the copied prefix. A rewound ordinal cannot select a new call or forget a prior uncertainty.

Do not branch replayed Workflow commands on a fresh client/history read or current Run ID comparison. The probe is a trusted external admission check, not a network call inside Workflow logic. A previously recorded probe Activity result is not current admission evidence after reset. Every SDK startup, materialization and protected Entity dispatch revalidates the current exact-run binding at its trusted boundary. A reset can race a probe; an observed run change invalidates the admission, and old-execution exclusion remains mandatory. The existing Entity intent prevents another scheduling decision regardless of reset detection timing. Lifecycle permissions deny direct reset/rollback of protected authority and deny ungoverned execution entrances.

The proposed `parked_state` Query exposes a typed reset observation: classification, observed/base/original Run IDs, history evidence reference, original lineage/call/ordinal, authority status, integrity status and allowed actions. While recording is pending or the Workflow Query is unavailable, the authenticated gateway exposes the same external admission hold to the operator. Persist a signed, exact-run-bound observation through the admitted message path after replay reaches a safe boundary; it must not alter copied historical commands. DSR-3.3/3.5 qualify observation delivery and replay; this is a proposed interface, not an existing API. `AgentPhase=PARKED` is a nonsecret discovery projection under DSR-3.4. Queries and Search Attributes supply no dispatch authority. Alert with `reset_review_required`, `transition_unverified`, `authority_missing_or_regressed`, or `workspace_integrity_unverified`; do not put native content in visibility metadata.

## Ordered operator runbook

1. The authorized operator asks the gateway to hold the exact session. Record the reset base, reset point, returned new Run ID, reason and observed branch. If the reset already happened outside the gateway, classify it with the same history probe. Do not start Claude, dispatch effects or assume the old execution stopped.
2. The maintainer retains the original start reservation, complete old/new history evidence, accepted-head references, package/policy/runtime/configuration identities, original call/input digest, ordinal/key and independent Entity identity. Refuse a new lineage, changed input at an existing ordinal, cleared claim tree or replacement authority. Missing, expired or regressed authority parks; restore cannot repair it.
3. Investigate every affected earlier outcome against independent authority and exact retained results. A lost admission reply retrieves the same intent/status/result. Inspect authorized external evidence where appropriate, without issuing another effect. A claim proves refusal/admission state, not a definitive Bash outcome. Absence of a result, process or marker does not prove NOT_RUN.
4. The independent controller inventories the exact old launch/container identity and confined descendants. Preserve required sole-readable result/postimage bytes before routine destructive cleanup. If urgent containment destroys them, record uncertainty or acknowledged-data loss. Obtain authenticated terminal evidence before admitting a replacement. Timeout, cancellation, process absence in a partial inventory and daemon unavailability do not prove whole-execution death. Do not clean unrelated processes. Already issued remote requests remain separately uncertain.
5. The authorized materializer validates the Session's independently retained accepted head, exact object versions/digests, conversation/pending/result/projection relation, workspace metadata and protected local claims. Check hidden/deleted/executable/link cases and configuration compatibility before restoring into a fresh execution. A generation counter detects some rollback but not every mid-run snapshot. An unchanged generation or valid-looking restored tree is insufficient. No local index reconstruction substitutes for accepted bytes.
6. Classify the result. Lost acknowledged accepted bytes is durability FAIL. Missing required outcome/postimage/projection, uncertain execution death or unverified authority/integrity parks with the concrete cause. If all exact definitive state was already retained, ordinary recovery may return that original result after all barriers pass; it neither redispatches nor manufactures an operator result.
7. Offer only the signed actions admitted for the stored cause in the next section. Bind the token to the original lineage, current park ID/digest, call identity, action payload, expiry, nonce and admitted key version. Reject stale or copied pre-reset actions and conflicting decisions. Record the disposition through the gateway and retain unresolved authority and evidence after termination.
8. Before service admission, DSR-3.5 proves reset to the first task, reset after handover, repeated reset, reset to an older run, changed ordinal/input, lost probe/admission reply, stale observation, partial claims, same-generation preclaim restore, missing/regressed authority and surviving descendants. The oracle is no second dispatch, no next model segment for uncertainty, exact original identity and replay-safe observation delivery. DSR-4.3 separately proves host/disk loss and live partition before portable admission.

## Signed actions and scope

The [approved Option R record](provenance.md#p-001) excludes `redo`, `release_claim` and keyed external service recovery. No action here clears claims, resets Entity authority, redispatches an uncertain effect or fabricates native results. A signed token proves an authorized decision, not the effect outcome or workspace integrity.

| Cause | Safe action rule | Refused action |
|---|---|---|
| Uncertain Bash | Proposed operator choice: signed `abort` only, retaining unresolved records and preservation-aware cleanup; awaiting confirmation | `retry`, `resume_from_checkpoint`, model continuation and a new effect identity used as recovery |
| Verified exact retained definitive result, with no uncertain Bash park | Ordinary exact recovery after authority, state and termination barriers; no new spawn | Rerun to recover output, latest-object restore or manually reconstructed result |
| Segment failure before any effect admission | Signed `retry` or `resume_from_checkpoint` only when affirmative nonexecution, exact input/state and all independent barriers are verified under DSR-3.3 | Retry based only on a timeout, missing marker or operator assertion |
| Missing/regressed authority or unverified integrity | Remain parked; signed `abort` can stop the logical session with evidence retained | Authority recreation, empty claims, speculative restore or continuation |

Operator decision pending: choose the proposed abort-only policy or leave action design open for a separately specified evidence-based reconciliation protocol. Manual investigation alone cannot supply an original exact native result and required postimage. Until the choice and DSR-3.3/3.5 proofs are complete, uncertain Bash continuation remains refused. Abort is logical termination, not business compensation, claim deletion or unconditional workspace destruction.

## Grounding and prior art

On 2026-10-14, Temporal Docs returned the official API definitions for [start-event original Run ID](https://dotnet.temporal.io/api/Temporalio.Api.History.V1.WorkflowExecutionStartedEventAttributes.html#properties), [reset marker fields](https://dotnet.temporal.io/api/Temporalio.Api.History.V1.WorkflowTaskFailedEventAttributes.html#properties) and [Continue-As-New transition](https://typescript.temporal.io/api/classes/proto.temporal.api.history.v1.WorkflowExecutionContinuedAsNewEventAttributes-1#properties). These are mutable documentation corroboration, not pinned-server execution proof. The distinction uses those explicit field contracts; `first_execution_run_id` and claim Run IDs are not reset detectors.

Atlas query/lookup led to public source reads of `api-go/history/v1/message.pb.go` (start fields) and `temporal/service/history/ndc/workflow_resetter.go` (`replayResetWorkflow` and `failWorkflowTask`). The resetter forks/rebuilds history and writes `RESET_WORKFLOW` with base/new Run IDs. Public source owners are [API history definitions](https://github.com/temporalio/api/blob/main/temporal/api/history/v1/message.proto) and [server resetter](https://github.com/temporalio/temporal/blob/main/service/history/ndc/workflow_resetter.go). No source execution or installation occurred. These reads establish mechanism precedent, not version-specific qualification of Server 1.32.0.

Reuse the [Entity pattern](https://docs.temporal.io/design-patterns/entity-workflow), [Continue-As-New handover](https://docs.temporal.io/develop/python/workflows/continue-as-new) and existing original-pending recovery owner. These supply partial precedent for the composed gateway/history/Entity/controller procedure. No complete arbitrary-Bash reset protocol is claimed as a sanctioned Temporal pattern. SDK substitution, generic engine replay, deterministic UUID generation and claim-only Run ID comparison are rejected as substitutes because they cannot establish this procedure's outcome and independent authority.
