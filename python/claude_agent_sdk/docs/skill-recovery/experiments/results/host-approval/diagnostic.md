# Signed verification harness diagnostics

The initial disposable signing run aborted its replacement Worker on a forged Ed25519 signature. Its Workflow imported the Ed25519 class through `workflow.unsafe.imports_passed_through()` but did not configure the whole cryptography extension as passthrough in the Worker runner. The native extension attempted late imports for `cryptography.exceptions.InvalidSignature`, emitted `SystemError: Objects/dictobject.c:2581: bad argument to internal function`, and aborted with `panic in a destructor during cleanup`. No signed approval success is established by that run. The parent later lost access to its dev server and recorded an RPC failure rather than a usable diagnostic history. The owned CLI was inventoried and safely cleaned. Original scratch logs and the failed report were preserved; this normalized note is the portable diagnostic record.

The bounded rig now configures both Worker and Replayer with `SandboxRestrictions.default.with_passthrough_modules("cryptography", "_cffi_backend")`. This configuration changes the proving boundary: the cryptography extension is passed through, so the result does not establish the proposed production verification package outside the passthrough set. Reproducing the initial crash requires removing that explicit runner configuration on both Worker and Replayer and sending the `forged signature` case; it is an authored harness diagnostic, not a candidate SDK recovery failure.

Independent review found that the first rejection helper accepted any exception as a refusal, including RPC failure or timeout. Those results are preliminary. The final helper requires `WorkflowUpdateFailedError` with `ApplicationError` cause of `ValueError` or `InvalidSignature`; the unsigned legacy tuple requires the specific argument decoder refusal (`RuntimeError: Failed decoding arguments`, with a `TypeError` cause). Other failures stop the experiment. The first strict rerun rejected the tuple correctly but failed the helper's too narrow expected type assertion. That failed report/history remains in scratch and supplies no final PASS claim. A subsequent preflight failed on an incorrect authored keyword to `WorkflowEnvironment.start_local` before any Workflow started; the keyword was corrected to `identity` without installing or changing dependencies.

The final [approve report](lead/approve/report.json) and [reject report](lead/reject/report.json) use the stricter check and explicit runner configuration. Each records eleven concrete refusals, exactly three accepted `review` Updates, duplicate acceptance across a further Worker replacement, and history replay. Preliminary generic exception reports are not the basis for these claims.
