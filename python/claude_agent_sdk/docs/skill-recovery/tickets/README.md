## What PASS means here

The end goal is reusable native Claude skill execution inside an application authored Temporal Workflow under the plugin's required registration, policy and security contract. Callers must not rewrite a validated skill package as a new agent loop. DSR-5.8 proves one bounded application authored Workflow scenario; it does not promise unrestricted compatibility with every Workflow. A later `temporal-agent-harness` adapter remains a separately verified Phase 7 deliverable, not a prerequisite for the plugin PASS.

PASS is a `verify-design` verdict of PASS on the specification and the plan, reached on evidence and not on paper review. The verdict needs three things.

1. Every row of the specification's `Assumptions and risks if wrong` table is settled. A row is settled when its status is `verified at source` with the proving artifact named, when evidence contradicted it and the design changed in response, or when the approved version 1 scope removed the design it covered and the row is marked `superseded`. A row that is still untested, inferred, relayed, a proposed fix or an open decision is not settled.
2. No open decision blocks the stated outcome. Each decision in the plan's M0 list that the approved scope needs has a named owner and a recorded answer.
3. An independent `verify-design` pass, run by fresh verifiers on the evidenced documents, returns PASS, and its manifest gate and proof of load both pass.

PASS scope. The stated outcome that the verdict judges is a durable skill execution plugin that is proven with a real model. It excludes upstream submission and the agent harness port, which Phase 7 covers. Rows A-35 and A-36 concern those two deliverables, so they stay open decisions until Phase 7, and the PASS report names them as outside the stated outcome. The plan's earlier pre M1 `verify-design` pass is dropped, because the Phase 1 real model evidence replaces it. DSR-0.2 records both statements, and DSR-0.3 applies them to the documents. A ticket added later for a CONDITIONAL finding takes the next free id in its phase and gets a row in the tables below.

## Conventions

- ID scheme: `DSR-<phase>.<n>` for a ticket and `DSR-P<phase>` for a phase epic. The root epic is `DSR-ROOT`. IDs are stable and never reused. A superseded ticket is marked superseded, not renumbered.
- Status is the first line after a ticket heading. Use OPEN, IN PROGRESS, DONE (with a date), or SUPERSEDED. Every ticket starts OPEN.
- Every ticket carries the field block shown in the template below, then the body from the `write-tickets` ticket format.
- Write concise technical English in the ASD-STE100 style: active voice, short sentences, one meaning per sentence, one term for one object. Do not use em dashes or en dashes. Do not join ordinary words with hyphens. Write each paragraph or list item on one source line.
- Source evidence cites the specification section by name (for example [canonical specification](../canonical-documents.md#specification), INV-1, *Claimed effect guard*), the assumption ids, and a stable external source: an official Temporal documentation URL, or a fork source permalink at the pinned commit. ## Priority, estimates and labels

Priority is the native importance value, recommended from the critical path to PASS. Urgent marks the unknowns that decide whether the design is viable at all (DSR-0.1, DSR-0.2, DSR-0.4, DSR-0.12, DSR-1.3 and DSR-1.10). High marks the rest of Phases 0 to 3 and Phase 6. Medium marks Phases 4 and 5. Low marks Phase 7, which is after PASS. A phase epic takes the highest priority among its tickets.

Estimates use the recommended default scale because no team scale exists: 1 point is about 4 focused work hours, and the scale is 1 to 5 points (about 4, 8, 12, 16 and 20 hours). The estimate covers the active work that produces the acceptance evidence and excludes waiting. A parent estimates only its own coordination. Work above 5 points is split. Each estimate states a confidence percentage, and an estimate below 80 percent is listed for operator confirmation in the index below.

Labels, by controlled category. Exactly one work type per ticket: `Type: Decision`, `Type: Research`, `Type: Build`, `Type: Verification`, `Type: Documentation`. Zero to two topics: `Topic: Engine`, `Topic: Effects`, `Topic: Approvals`, `Topic: Workspace`, `Topic: Versioning`, `Topic: Assumptions`. Zero or one status flag: `Status: Blocked on decision`. No ticket carries a planning period, because all of them are backlog.

## Phase gates

Ids are never renumbered, so a ticket added later takes the next free number in its phase even when an exit review already holds a lower number (DSR-3.8 follows the Phase 3 exit review DSR-3.7, and the exit review is blocked by it). Phase 0 has no exit review ticket: DSR-0.3 and the decision records close it. A phase ends with an exit review ticket. The exit review updates the specification's assumption rows and the plan's milestone text with the evidence, and records a continue or redesign decision. A contradicted assumption stops the next phase until the design change is recorded.
